# The method, end to end (read this before writing the paper)

## PART I: pipeline, language, evaluation

This document describes the system **as implemented** (code in `usg/`), with the formal definitions, a worked example produced by the real code, what is
tested, and what is not. It contains no paper prose on purpose. Numbers in the results section come from `paper/results/` (generated by `usg/scripts/`).

---------------------------------------------------------------------------------------------------------------------------------------------

## 0. The idea in five sentences
1. A guided pedestrian task is **one kind of object: a goal formula plus safety formulas**, written in a small **typed specification language**
   (atoms that return numeric margins + temporal combinators). "Reach a target" is only the most common goal; reaching, waiting, holding, looking, following,
   keeping clear, pacing and signal compliance are all *expressions in the same language* (library definitions), not separate task classes or code paths.
2. A local 4B LLM writes that specification **as data** (JSON, never executed), then a short world-building script (user, vehicles, signals). A map-aware validator
   checks both; errors go back to the model.
3. The result is a standard **OpenSCENARIO** file whose `<VRTask>` elements carry the formulas; the map is **OpenDRIVE**.
4. A WebXR/first-person **player** monitors the formulas live on the *real* pose of the participant (the human is the ego pedestrian) and reports pass/fail and
   **numeric margins** (metres, degrees, m/s).
5. The 7 scenario types of the earlier taxonomy become **named points on constraint axes** that are *derived from the formulas*.

What is inherited, what is new (be precise in the paper): see section 10.

**Two parts:** Part I (sections 0-12) is the pipeline, the specification language, evaluation and limitations; **Part II (A-S, at the end)** is the lowest level: every constant, OSM tags → roads, junctions, crossings, surfaces, routing graph, OpenDRIVE, scenario file, procedural 3D meshes and sizes, camera and movement, sandbox and model settings.

## 1. Data flow

```
 OSM area / .osm file / synthetic city          text prompt
            │                                        │
            ▼                                        ▼
  osm.build_map ─► MapModel (metric ENU frame) ─┬─► agent (Qwen3.5-4B, local, tool-calling loop)
     roads, sidewalks, crossings, signals,      │        │ pre-fetch: overview, reference script,
     props, buildings, ped. graph, OpenDRIVE    │        │            reference SPECIFICATION (L1/L2)
                                                │        ▼
                         stage A (L1, L2) ──────┼──► submit_spec  ─► spec.document.check_document   (data, never executed)
                                                │        │            parse + type-check + resolve map refs + feasibility
                                                │        ▼
                         stage B ───────────────┴──► submit_script ─► sandbox (AST policy, restricted runtime, subprocess + Job Object)
                                                         │              scenario = ScenarioBuilder(...); scenario.apply_spec(SPEC)
                                                         ▼
                                           validate (map rules, derived-from-formula rules)  +  nominal walker margins
                                                         │  errors → back to the agent (repair loop)
                                                         ▼
                      scenario.xosc (+ <Spec> formulas) · map.xodr · scene_map.json · spec.json · script.py · package
                                                         ▼
                              player (three.js/WebXR): parses <Spec>, 10 Hz trace of the real pose, interval monitor, margins, results JSON
```

Levels compared in the evaluation: **L0** the model fills in a Python script that calls task helpers (`go_to`, `cross`, `follow_path`) — the original
system; **L1** specification from the standard library, then world script; **L2** like L1 and the model may also write its own definitions.

## 2. The map model (`usg/src/usg/osm.py`, `mapmodel.py`, `pedgraph.py`, `xodr.py`)
* OSM is projected once to a local East-North frame, metres, heading 0 = east, counter-clockwise. Every component uses these coordinates.
* `MapModel`: roads (split at shared nodes, trimmed at junctions), sidewalks (offset polylines; a 2 m default on residential/secondary roads when untagged),
  crossings (rectangle: centre, heading, length, width), signals, props (bench, bus stop, lamp, tree, bollard, waste basket, …), buildings, areas, paths, railways.
* `surface_at(p)` ∈ {crosswalk, building, water, road, sidewalk, path, ground} with fixed priority. It is the single source of truth; the TypeScript port is
  tested against Python on 13,440 sampled points.
* Pedestrian routing graph (A*, crossing penalty) for feasibility checks and the nominal walker. OpenDRIVE export with junction connecting roads (structurally
  verified, **not** validated against esmini/XSD).

## 3. The task model

### 3.1 One task form plus constraint axes
A task is a goal formula (default form: reach a zone; others: hold, wait for green, look, follow, keep clear, pace) under safety formulas. The constraints live on **axes** (`spec/axes.py`); a scenario's value on each axis is *derived from its formulas*:

| axis | values | derived when |
|---|---|---|
| surface | walkable / crossing / road | goal zone: centre on road → road; crosswalk or crossing rectangle → crossing; else walkable |
| path | free / corridor | a `near_path` or `on_surface` atom occurs |
| static | none / obstacles | a `dist_ge` atom on a non-moving entity |
| dynamic | none / movers | a `dist_ge` atom on a moving entity |
| signal | none / obeyed | a `signal_is` atom occurs |
| composition | single / ordered / unordered | ≥2 tasks with mode sequential / parallel |

The 7 types are named points: `ptp_env` (base), `ptp_road` (surface=road), `cpath` (path=corridor), `env_con` (static=obstacles), `dyn_nav` (dynamic=movers),
`dep_comp` (ordered), `indep_comp` (unordered). The taxonomy table in the earlier draft (5 navigation categories + 2 composite) is exactly this set; the axes make the
overlap between categories explicit and let a single scenario combine several constraints (e.g. cross on green with a car approaching).
Signal compliance is an axis but has no named type: it is a rule, not a task. Object interaction (pick up / place), crowds, wayfinding by instruction and
perception tasks are **out of scope** (future work).

### 3.2 A task (`dsl/core.py: VRTask`, `dsl/builder.py: apply_spec`)
`name`, `instruction` (HUD text), **`goal`** formula (success when satisfied), **`safety`** formulas (the task fails as soon as one is violated), `timeout`
`{initial, baseline}` (a hint is raised at `initial`; the task fails at `baseline`), `after` (run after these tasks), optional `group`/`mode`
(sequential | parallel | independent), `required`, `start_time`. Tasks made with the older helpers (`go_to`, `cross`, `follow_path`) are **compiled to the same
formulas** (`_compile_legacy`), so there is one evaluation path; `spec_raw` keeps their readable macro form and `spec.document.document_from_spec` exports it
(round-trip tested for all 7 reference scenarios).

### 3.3 The language (`spec/formula.py`)
Formulas are JSON objects with an `op`. **Atoms** (all evaluated on a *sample* = pose + world at one instant):

| atom | fields | margin ρ (positive = satisfied) |
|---|---|---|
| `true` | – | +∞ |
| `in_zone` | zone | disc: r − dist(user, centre); rect: min(hl − \|u\|, hw − \|v\|) in the rectangle's frame; entity zone: r − dist(user, entity centre) |
| `on_surface` | surface | +1 if the surface under the feet is in the class, else −1 (qualitative) |
| `near_path` | path, tol | tol − distance to the polyline |
| `dist_le` / `dist_ge` | entity, d | d − δ / δ − d where δ is the distance from the user to the entity's *oriented bounding box* |
| `look_at` | entity or point, angle | angle − angular error between gaze yaw and the bearing to the target (degrees) |
| `speed_le` / `speed_ge` | v | v − speed / speed − v |
| `signal_is` | signal, state | +1 / −1 |
| `event` | name | +1 if the storyboard event has started, else −1 |

Zones: `disc{x,y,r}`, `rect{cx,cy,h,hl,hw}`, `entity{name,r}`; symbolic forms `crossing{id}`, `crossing_side{id,side,r}`, `feature{id,r}` are resolved against the map before
encoding. **Combinators**: `not, and (min), or (max), implies, eventually[a,b], always[a,b], until[a,b], then, prev`. `then(φ1,…,φn)` is sugar for
`eventually(φ1 ∧ eventually(φ2 ∧ … eventually(φn)))`. Windows are seconds from the task start; `end: null` means "until the task ends".

### 3.4 Quantitative semantics (`spec/monitor.py`; TypeScript twin `player/src/runtime/monitor.ts`)
Time is sampled at dt = 0.1 s. For a trace prefix the monitor returns an **interval** `(lo, hi)` for a formula anchored at sample k:
atoms are exact where the sample exists and `(−∞, +∞)` beyond the prefix; `not` swaps the bounds; `and/or` take min/max componentwise;
`eventually` takes the max over the window (unknown samples can still help → `hi = +∞`), `always` the min (unknown samples can still hurt → `lo = −∞`);
`until` is `max_j min(ρ_right(j), min_{i<j} ρ_left(i))`; `prev` reads the previous sample (`init` before the first). With a **complete** trace `lo = hi` and
this is the standard STL robustness. Decision rule for a task: **violated** if any safety rule has `hi < 0`; **satisfied** if the goal has `lo ≥ 0`; **failed** if the
goal has `hi < 0`; otherwise undecided. Consequences worth stating in the paper: a failure or success is detected *at the earliest moment it is determined*,
not only at the end; windows close exactly when their time has passed.

### 3.5 Definitions and the standard library
A `call` node expands a definition by substituting parameters (`{"param": "x"}` placeholders) into its body; expansion is checked again after substitution.
Limits: ≤12 own definitions, call depth ≤6, no recursion, ≤400 nodes and depth ≤14 after expansion. The standard library (written in the language itself):

| name | meaning (core formula) |
|---|---|
| `reach(zone)` | `eventually in_zone` |
| `reach_within(zone,s)` | `eventually[0,s] in_zone` |
| `cross(far_zone)` | `eventually in_zone(far side)` |
| `hold(zone,s)` | `always[0,s] in_zone` |
| `wait_for_green(zone,signal)` | `in_zone until signal_is(green)` |
| `look(entity,angle,s)` / `look_point(point,angle,s)` | `eventually[0,s] look_at` |
| `follow(entity,d,s)` / `keep_clear(entity,d,s)` | `always[0,s] dist_le(d)` / `always[0,s] dist_ge(d)` |
| `pace(vmin,vmax,s)` | `always[0,s] (speed_ge ∧ speed_le)` |
| `collision_free(entity,r)` | `always dist_ge(entity,r)` (r = 0.3 m, the participant's radius) |
| `stay_on(surface)` | `always eventually[0,1] on_surface` (1 s grace) |
| `stay_near_path(path,tol)` | `always eventually[0,1] near_path` (1 s grace) |
| `obey_signal(zone,signal)` | `always ((in_zone ∧ prev ¬in_zone) → signal_is(green))` — only *entering* on red violates; the light changing while crossing is fine |
| `no_event(name)` | `always ¬event` |

### 3.6 Encoding in the scenario file
Inside the standard `UserDefinedAction/CustomCommandAction type="VR_TASK"` the `<VRTask>` carries `Goal`, `Target`, `Instructions`, `Feedback`, `DependsOn`,
`Constraints`, `FailureCondition` (the two timeouts), and `<Spec origin="spec|helper"><Goal><F op=…/></Goal><Safety><F op=… label="crossed on red"/>…</Safety></Spec>`.
`label` is what the participant is told when that rule fails. Other tools that ignore custom commands still load the file.

## 4. Generation (agent, stage A, stage B)
* **Model:** Qwen3.5-4B Q4_K_M from the user's LM Studio files, run by LM Studio's bundled llama.cpp (Vulkan, AMD Radeon iGPU) on 127.0.0.1:8089, thinking disabled,
  temperature 0.2, context 16,384 in the evaluation. ≈14 tok/s generation, ≈170 tok/s prompt processing.
* **Tool protocol:** plain-text `<tool name="…">{json}</tool>`; `submit_script` takes a fenced `python` block; `submit_spec` takes JSON (a bare ```json block with `tasks`+`goal`
  also counts). Tools: `get_map_overview, list_features, get_feature, check_point, plan_route, list_scenario_types, get_scenario_template, record_plan,
  list_atoms, submit_spec, submit_script`. Arguments are parsed leniently; errors show a working example.
* **Harness pre-fetch** (saves a small model from over-exploring): map overview; reference script of `classify(prompt)[0]`; for L1/L2 also a *reference specification*
  obtained by running that script and exporting its tasks (`document_from_spec`). Guards: repeated identical calls, repeated identical validator error, ≥5 lookups,
  ≤6 rejected specifications, ≤6 rejected scripts, 16 steps (22 for L1/L2).
* **Stage A (`spec/document.py: check_document`)** — no code runs: structure/type check with JSON-path errors, definitions expansion, map-reference resolution
  (unknown crossing id → error), zone centre not in a building/water, consecutive zones routable, baseline ≥ initial, time windows vs timeout; it returns *what the script must
  create* (entities, signals, events referenced by the formulas).
* **Stage B** — the world script runs in the sandbox (AST policy → restricted builtins → subprocess with scrubbed env + Windows Job Object); it receives `SPEC`
  (plain dict) and must call `scenario.apply_spec(SPEC)` (otherwise `spec_not_applied`). If it omits `scenario.user(...)` the participant is placed automatically on the
  walkable network ≈18 m (route distance) before the first goal zone, facing it.
* **Validator (`validate.py`)** — map rules (starts on valid surfaces, vehicles on roads/lanes, routes, timeouts vs walking time at 1.2 m/s, signals defined, parked cars not on the user…) and
  formula rules (unknown entity/signal/event, window beyond timeout, a moving obstacle that never comes within 6 m of the participant's path); the seven archetype checks now read
  the formulas. `scenario_type="custom"` skips the named-type check.
* **Hard checks of the request (`usg/grounding.py`, `sandbox.py`, `validate.py`)** — (1) before the model runs: the prompt names an object the map does not contain (waste basket, bench, bus stop, lamp, tree,
  bollard, bicycle parking, zebra / signalised crossing, any crossing) → refused with an inventory of what the map has; (2) on submission: a requested object that no goal zone reaches → rejected with the nearest ids;
  explicit cues must be honoured ("onto the road" → a goal zone on the carriageway; "wait for the light" → a signal state in the specification; "look at …" → `look_at`; approaching traffic → a vehicle that is kept clear of; parked cars →
  parked vehicles that are avoided); (3) the world script must apply *exactly* the accepted specification (`spec_modified` otherwise); (4) a model-written safety rule that an ordinary walk from the start to the goal already breaks is an error
  (`spec_rule_violated_by_nominal`, e.g. "stay on the road" while the participant starts on the sidewalk).
* **Nominal walker (`spec/oracle.py`)** — a synthetic participant used *only* to check satisfiability: it follows the pedestrian route through the goal zones in formula order at 1.3 m/s,
  waits for hold windows / for green, waits at crossings gated by `obey_signal`, yields to approaching movers it must keep clear of, and keeps its gaze on look targets. The
  *same* monitor evaluates the formulas on that trace; the result is a margin per task. A negative margin is a **warning** (it can also mean the walker's policy is too simple), never an error.
  It does not run in the player; the participant is never moved by software.

## 5. The player (`usg/player`)
Parses the scenario including `<Spec>`; simulates vehicles/walkers/signals from the storyboard; for each active task records a **10 Hz trace** of the real pose
(position, camera yaw as gaze, speed from consecutive samples, surface class, referenced entities' oriented boxes, signal states, started events) and evaluates the
formulas (every 40 ms on an in-progress provisional sample so that instantaneous violations such as a collision are caught immediately). Success/failure follow the decision rule of 3.4;
the failing rule's `label` is shown. Hard timeout and the "hurry up" hint use the two timeouts. At the end it exports per-task outcome, time, minimum vehicle distance,
goal margin and tightest safety margin, plus the 10 Hz walking trace. The inspector (key I) shows each task's formulas with live margins. VR and first-person desktop share this
code; **real headset sessions have not been tested.**

## 7. Worked example (output of the real code, synthetic city)
Specification (stage A accepted; it asks the script to create `Car1` and the signal `signal_1`):
```json
{"tasks": [
 {"name": "check_traffic", "instruction": "Look at the approaching car.",
  "goal": {"op": "call", "name": "look", "args": {"entity": "Car1", "angle": 40, "seconds": 12}}, "timeout": {"initial": 20, "baseline": 30}},
 {"name": "wait_then_cross", "instruction": "Wait for green, then cross.", "after": ["check_traffic"],
  "goal": {"op": "then", "args": [
     {"op": "call", "name": "wait_for_green", "args": {"zone": {"kind": "crossing_side", "id": "crossing_1", "side": "start", "r": 3}, "signal": "signal_1"}},
     {"op": "call", "name": "cross", "args": {"far_zone": {"kind": "crossing_side", "id": "crossing_1", "side": "end", "r": 2}}}]},
  "safety": [{"op": "call", "name": "obey_signal", "args": {"zone": {"kind": "crossing", "id": "crossing_1"}, "signal": "signal_1"}},
             {"op": "call", "name": "collision_free", "args": {"entity": "Car1", "r": 0.3}}],
  "timeout": {"initial": 90, "baseline": 130}}]}
```
World script (stage B): the car drives along the road when the first task is done; the signal cycles red 14 s / green 12 s; the participant is placed automatically.
After expansion the second task is
```
goal   : eventually[0,inf]( (in_zone(disc(12.0,-4.2; r=3)) until[0,inf] signal_1=green)
                             and eventually[0,inf]( eventually[0,inf]( in_zone(disc(12.0,4.2; r=2)) ) ) )
safety : "crossed on red"    always[0,inf]( (in_zone(rect(12.0,0.0)) and prev(not in_zone(rect(12.0,0.0)))) -> signal_1=green )
         "collision with Car1" always[0,inf]( dist(Car1) >= 0.3 )
```
Derived axes: `dynamic=movers, signal=obeyed, composition=ordered` (surface of the first task has no zone, the second is a crossing). The validator accepted it; the nominal walker
obtained goal margins +40.0 (task 1: 40° of slack in the look angle) and +1.0 (task 2), and rule margins +0.09 (`crossed on red`: at the closest the walker waited 9 cm short of the crossing edge while the light was red) and +6.7 (`collision with Car1`: it stayed 7.0 m from the car's box, 0.3 m being the limit). In the file, the second `<VRTask>` contains
`<Spec origin="spec"><Goal><F op="eventually" start="0"><F op="and"><F op="until" …>…` (see `usg/player/tests/fixtures/spec_cross.xosc` for a complete file).

## 8. Quantitative evaluation (RQ2, RQ3) — protocol
* **Prompts** (`usg/eval/prompts.json`): 32 — 21 for the 7 named types on the synthetic city (3 phrasings each), 4 *mixed* prompts that need signal compliance, a car and/or `look_at`
  (capabilities the task helpers do not have), and 7 on a real map (Munich old town, cached OSM: narrow one-way streets, uncontrolled crossings, no signals).
* **Pipelines:** keyword baseline (classify the prompt, run the reference script of the guessed type, no model), L0, L1, L2; ×3 repetitions (sampling at temperature 0.2).
* **Metrics (all automatic):** *valid* = the validator accepted the final scenario; *first try* = accepted at the first submission (= no repair loop; for L1/L2 the first specification and the first
  script); *adherent* = the scenario's constraint axes equal the axes the prompt asks for (every other constraint axis at its default) **and** required operators occur (e.g. `look_at`);
  *recall* = fraction of requested axes present; *nominal ok* = the nominal walker satisfies all tasks; steps and wall-clock time.
* **Statistics:** Wilson 95% intervals; paired comparisons by exact sign test on (prompt, repetition) pairs.
* **Limits of the protocol (state them):** prompts were written by the author; one model (4B); adherence is judged on constraint axes, not on whether the text of the instruction is good;
  a prototype run on two prompts informed the final prompts/harness (the benchmark prompts were not otherwise tuned); the nominal walker is an idealised participant.
* **Vision ablation:** the same L2 pipeline with an *annotated top-down map image* attached to the first message (`render.map_image_png`: north up, metric grid with coordinates, crossing /
  bus-stop / road ids). Qwen3.5-4B is multimodal (LM Studio stores its vision projector `mmproj-*.gguf` next to the GGUF; llama-server is started with `--mmproj`). 2 repetitions of the 32 prompts,
  compared with the text-only L2 runs of the main benchmark (same weights and sampling; the vision server additionally loads the projector). Condition label in the data: `2v`.
* **Not evaluated:** participants (no user study; RQ4 is a small qualitative round), real headset sessions, other model sizes (only one model is installed).

Results: see section 9 (generated), `paper/results/summary.md`, `runs.csv`, `benchmark.jsonl`.

**Development history that must be stated in the paper (the prompts were not changed, the system was tuned on them).** Four pilot runs over these same prompts (`pilot0_discarded`, `pilot1_old_code`,
`pilot2_before_corridor_fix`, `pilot3` in `paper/results/`) exposed faults that were fixed before the final run: (1) the model adapted the reference script and made mistakes in start-position code that is not needed
(fix: after an accepted specification the tool answer gives the exact two-line world script, or the list of entity/signal names to create; `scenario.user()` may be called without a start);
(2) the automatic start of the participant ignored corridor rules, so an ordinary walk violated them at the first sample (fix: the start is chosen inside the corridor, `_ensure_user`);
(3) the error text for "stand on the road" now includes a concrete goal zone verified to be on the road; (4) a 16k context overflowed once (final run: 24k). The reported numbers are from the final run only, with the code fixed.
Remaining failures are model behaviour (stops calling tools, picks a signalised crossing hundreds of metres away so the timeout is too short, script mistakes, ordered vs unordered composition).

**Earlier benchmark (synthetic city + Munich, L0/L1/L2 comparison and vision ablation): not run; optional ablations.** `paper/results/benchmark.jsonl` holds the keyword baseline (32 prompts) and 5 smoke runs only.
Keyword baseline (32 prompts): all scenarios valid; adherent 59% (0% on the 4 mixed prompts; 67% on the 21 named-type prompts; 71% on the 7 real-map prompts).

## 10. Relation to prior work (verified against the papers where stated)
* **GUsT-3D** (Wu et al. 2022; PDF read): defines guided user tasks as constraint lists over annotated scenes (layers: navigation, object, interactive, environment; relations `near`,
  `visible`, `LookAt`, `onTopOf`, localisation; evaluation times *at a time / at some point / at all times*; a hint after a delay and failure at the time limit; JSON logs; Unity tooling;
  an outdoor crossing case study). **Inherited ideas:** tasks as time-quantified constraints, the two-stage timeout, surface/signal/look constraints. **Not in the GUsT-3D paper:** the words
  Target/FailureCondition, dependent/independent composite groups, OpenSCENARIO/OpenDRIVE/OSM, generation of any kind. **New here:** the specification language with numeric margins evaluated live
  on the real pose; map-derived navigable space instead of manual annotation; LLM generation of tasks and worlds with validation and repair; standard-format encoding; traffic and signals in the scenario.
  Object interaction (take/place/activate) is deliberately out of scope.
* **LLM scenario generators for driving** (ScenicNL, ChatScene, ChatDyn, Text2Scenario, LLM4AV, TARGET, …): vehicle-under-test, no human performing generated tasks. LLM4AV
  (text → DSL → OpenSCENARIO on OpenDRIVE with a multi-layer validator, includes a pedestrian crossing) is the closest pipeline-level work; read it before claiming novelty.
* **Specification → scenario two-stage designs** (TARGET: rules → DSL → scenario; Traffic Scenario Orchestration via constraint satisfaction; Extended-Scenic pipeline): same shape in the driving domain.
* **Safe wording for the claim:** *to our knowledge, existing LLM-to-OpenSCENARIO work targets a vehicle under test; we generate pedestrian guided tasks for a human participant, grounded in a real map, validated with a
  quantitative task specification, and played in VR or first person.* Do not write "first".

## 11. Limitations and honest caveats
* The request checks are keyword based: objects outside the list (fountain, statue) and cues phrased differently are not checked.
* No participant has played a scenario; VR on hardware, controller locomotion and the in-VR HUD are untested; `look_at` uses camera yaw (head in VR, mouse on desktop), not eye tracking.
* Props are procedural placeholders; the map depends on OSM tags (sidewalks assumed on residential/secondary roads when untagged); OpenDRIVE is not validated against esmini/XSD.
* A 4B model follows nuanced prompts only partly; the benchmark measures how often; failures are analysed in `summary.md`.
* Qualitative atoms (`on_surface`, `signal_is`, `event`) give margins ±1, not distances.
* The nominal walker is an idealised policy; a negative margin is advice, a positive one is no guarantee that a human can do it.
* Margins from the player are computed on a 10 Hz trace (provisional sample every 40 ms); a frame step larger than 0.1 s repeats the last sample.

# PART II: every constant and rule below the pipeline level
How the map and the 3D world are built from OSM, where each size comes from, how routes and OpenDRIVE are produced, how the scenario file and the player are built, and every constant (file and function in brackets; read from the code). Nothing here is learned or generated by a neural model: **every size is an OSM tag value or a constant listed here.**

## Part II · A. From a rectangle to OSM data

1. **Selecting the area** (`web/mapselect.html`, `app.py`): the picker is a Leaflet map (OpenStreetMap tiles, Nominatim search) in an iframe. The rectangle is posted to
   `POST /api/bbox` as `{south, west, north, east}` and validated (`-90 <= south < north <= 90`, `-180 <= west < east <= 180`). Area `A = |Δlat·111.32| × |Δlon·111.32·cos(mid-lat)|` km²;
   the limit is 1 km² (`MAX_AREA_KM2`). "Use current view" shrinks the visible bounds around their centre by 5 % steps until `A ≤ 0.98 km²`.
2. **Download** (`osm.fetch_osm`): one Overpass request (`[out:xml][timeout:90]`, HTTP timeout 120 s, `User-Agent: usg/0.1`) for, inside the box: ways with `highway`, `building`, `barrier`, `railway`,
   `natural=water`, `leisure=park|garden`, `landuse=grass|forest`; nodes with `highway`, `amenity=waste_basket|bench|bicycle_parking`, `natural=tree`, `public_transport`, `barrier=bollard`;
   plus all nodes of those ways (`(._;>;);out;`). The file is cached as `.usg_cache/osm_<12 hex of sha1("S,W,N,E")>.osm`, so a repeated area is offline.
3. **Parsing** (`osm.parse_osm`): nodes `(lat, lon, tags)` and ways `(node ids, tags)` from the XML.

## Part II · B. Projection (`geo.Projection`)
A single local tangent-plane frame around the **centre of the box** (or of all nodes if no box): `x = R·Δlon·cos(lat0)`, `y = R·Δlat`, `R = 6,378,137 m`; x east, y north, metres.
Heading is `atan2(dy, dx)`: 0 = east, counter-clockwise (the OpenDRIVE/OpenSCENARIO convention). The map is projected exactly once; every later component reads the metric data.

## Part II · C. Roads (`osm.build_map`, `mapmodel.py` constants)
* **Which ways:** `highway ∈ {motorway, trunk, primary, secondary, tertiary, unclassified, residential, living_street, service, *_link}`, ≥2 nodes, not `area=yes`.
  Footways, paths, pedestrian streets, cycleways, steps and tracks are *paths* (section G), not roads.
* **Splitting:** a way is cut at every node that other road ways share or that ends a way: a node counts `+2` if it is the first/last node of a way and `+1` otherwise;
  nodes with count ≥2 become cut points. Each piece (≥0.5 m long) is a `Road` with id `road_<n>`, its start/end node ids and `osm_way`.
* **Direction/lanes/width:** `oneway` if tagged yes/true/1 or `motorway`. `lanes` = tag, else 1 for oneway or service roads, else 2. `width` = tag `width` (leading number), else
  `lanes × 3.25 m` (`LANE_W`), else 4.0 m for `service`. `speed` = `maxspeed` (km/h, or mph × 0.44704) else the class default (m/s): motorway 33.0, trunk 25.0, primary/secondary/tertiary 13.9,
  residential 8.3, living_street 4.2, service 5.5, otherwise 8.3.
* **Sidewalks** (`_sidewalk_widths`, `DEFAULT_SIDEWALK_W = 2.0 m`): tag `sidewalk=both|yes` → both sides, `left`/`right` → that side, `no|none|separate` → none; `sidewalk:left/right/both=yes` also count.
  If the tag is absent and the class is primary, secondary, tertiary, unclassified, residential, living_street or a link, **both sides get 2.0 m by assumption** (this is the map's main data-quality caveat).
  "Left"/"right" are relative to the way's digitised direction.

## Part II · D. Junctions and trimming
A node with ≥3 incident road ends is a `Junction` (`junction_<n>`): `radius = max over incident roads of (width/2 + max(sidewalk widths)) + 2.0 m`. Each incident road is trimmed at that end by
`min(radius, 0.45·length)` (`trim_start/trim_end`; the road is drawn and exported only between the trims). `_junction_geometry` builds, per junction: the asphalt polygon (for every incident
end, sorted by outward heading, the two edge points `±width/2` at the trim point) and **corner patches** (for each neighbouring pair the quadrilateral between the sidewalks of the two roads,
width = the larger of the two sidewalk widths).
Signalised junction: a `traffic_signals` vehicle node within `radius + 15 m`.

## Part II · E. Signals and crossings
* **Signals:** nodes with `highway=traffic_signals` or `crossing=traffic_signals`; each stores its nearest road; `kind = pedestrian` if the node is a `highway=crossing`, else vehicle.
* **Crossing candidates:** nodes `highway=crossing` or `railway=crossing`, and the midpoint of ways `highway=footway + footway=crossing`.
* **Accepted if** the nearest road centre-line is within `width/2 + 4 m`. Its position is projected to the road and clamped to arc length `[trim_start + 3.0, length − trim_end − 3.0]`;
  a candidate within 4 m of an existing crossing is dropped.
* **Geometry:** centre on the road centre-line; `heading = road heading + π/2` (the walking direction across); `length = road width` (the span across the road); `width = 3.0 m` (depth along the road).
  `endpoints()` = centre ∓ (length/2)·(cos h, sin h): **start = the road's right-hand kerb, end = the left-hand kerb.**
* **Control:** `signals` if `crossing=traffic_signals`, `crossing_ref=pelican`, or a signal lies within 18 m on a `highway=crossing` that is not tagged zebra (the nearest signal is linked, both ways);
  `zebra` if `crossing=zebra|marked` or `crossing_ref=zebra`; otherwise `uncontrolled`. A crossing without an OSM signal still gets the virtual pedestrian signal name `<crossing id>_ped` when a scenario cycles it.

## Part II · F. Props (street furniture)
Nodes become props with id `<type>_<n>`: `highway=bus_stop` (or `public_transport=platform|stop_position` with `bus=yes`) → `bus_stop`; `amenity=waste_basket` → `waste_basket`; `amenity=bench` → `bench`;
`natural=tree` → `tree`; `highway=street_lamp` → `street_lamp`; `barrier=bollard` → `bollard`; `amenity=bicycle_parking` → `bicycle_parking`. Each stores its nearest road. Bus stops, benches and bicycle parking
are **aligned to face the road**: heading = road heading at the nearest point, rotated by +π/2 if the prop is on the right of the road, −π/2 if on the left; other props keep heading of the road.

## Part II · G. Polygons, lines, paths
* **Buildings:** closed ways with `building`, ≥4 points, oriented counter-clockwise; `height = height tag` else `building:levels × 3.0 m` with 3 levels assumed; at least 3.0 m.
* **Barriers:** `fence, wall, hedge, guard_rail, retaining_wall, city_wall`; height tag else 1.2 m.
* **Areas:** water (`natural=water` or `waterway=riverbank`, closed); green (`leisure=park|garden`, `landuse=grass|forest`, `natural=wood`, closed).
* **Paths:** `highway ∈ {footway, path, pedestrian, cycleway, steps, track}` excluding crossings and sidewalk-tagged footways; width tag else 6.0 m for `pedestrian`, 2.0 m otherwise.
* **Railways:** `rail, tram, light_rail, subway` lines (treated as barriers for pedestrians).
* `bounds` = bounding box of road points and building points.

## Part II · H. The surface model (`MapModel.surface_at`, ported line-for-line to `player/src/runtime/surface.ts`)
The class of a ground point is the first rule that matches, in this order:
1. **crosswalk:** inside a crossing rectangle (`|u| ≤ length/2` and `|v| ≤ width/2` in the crossing's frame);
2. **building:** inside a building polygon (bounding-box prefilter + ray casting);
3. **water:** inside a water area;
4. **road:** for any road, `|t| ≤ width/2` (t = signed distance from the centre-line); or inside a junction disc of radius `0.8·radius`;
5. **sidewalk:** within `width/2 + sidewalk width` on the side that has a sidewalk (side by the sign of t);
6. **path:** within `path width / 2` of a path polyline;
7. **ground.**
`WALKABLE = {crosswalk, sidewalk, path, ground}`, `PED_INFRA = {crosswalk, sidewalk, path}`; the specification's surface classes map to these sets (`monitor.SURFACE_SETS`).

## Part II · I. Pedestrian routing graph (`pedgraph.py`)
* **Nodes** are placed on the *centre line of each sidewalk* (offset polyline at `±(width/2 + sidewalk/2)`; a 1.0 m "verge" is used for routing when a side has no sidewalk) at both ends of the trimmed road,
  every `STEP = 12 m`, and at the arc length of every crossing on that road. Consecutive nodes are connected by `sidewalk`/`verge` edges.
* **Crossing edges** connect the right-side and left-side node nearest to the crossing's arc length. **Corner edges** link the left sidewalk end of one road to the right sidewalk end of the next road around each junction.
  **Weld edges** join road ends of different roads within 6 m. **Path edges**: each path is resampled every 12 m and its two ends are joined to the nearest graph node if within 15 m.
* **Routing:** A* on Euclidean distance, `CROSSING_PENALTY = 4.0 m` added per crossing edge (prefers fewer crossings); start and goal snap to the nearest node; the result is the polyline
  start → nodes → goal with its length and the crossings used. Crossings can be forbidden per call.

## Part II · J. OpenDRIVE export (`xodr.py`; OpenDRIVE 1.6, right-hand traffic)
* Header with the map bounds and a `+proj=tmerc` georeference at the projection origin.
* **One `road` per trimmed map road:** `planView` = one `line` geometry per polyline segment (heading from the segment), length = sum; links to the neighbouring road or to the junction at each end;
  `type town` with `speed max` in m/s; flat elevation.
* **Lanes:** lane width `w = width / n` where `n = lanes` for one-way roads (all on the right, ids −1…−n) and `width / (2·(lanes // 2))` per lane for two-way roads (`lanes // 2` each side, at least 1).
  Sidewalk lanes (`type sidewalk`, the map's sidewalk width) outside the driving lanes (id `n+1` left, `−(n+1)` right). Centre lane 0 with a yellow marking (broken on two-way roads); a white solid edge mark.
* **Objects/signals:** each crossing is an `object type=crosswalk` (s relative to the trimmed road, `hdg = π/2`, `length = crossing length`, `width = 3.0`, height 0.02); each signal is a `signal`
  with `s,t` from projecting its position, `zOffset 2.5`, type code 1000001 (vehicle) / 1000002 (pedestrian).
* **Junctions:** for every pair (incoming lane, outgoing lane) allowed by direction, one **connecting road** that is the polyline `entry point → junction centre → exit point` with a single lane of the
  smaller of the two lane widths and lane links; one `connection` per pair.
* **Verification:** structurally tested (road count = roads + connections, links); **not validated against esmini or the OpenDRIVE XSD.**

## Part II · K. Map helpers used by scripts and tools (`dsl/core.py: MapQuery`)
* `crossing_side(id, side, inset)`: the point beyond one end of a crossing: for `"start"` the right kerb endpoint moved `inset` metres *backwards* along the walking direction (default 1.5 m; the specification's `crossing_side`
  zone uses 1.0 m), heading across the road; for `"end"` the left kerb endpoint moved `inset` metres forward, heading reversed.
* `along_road(road, s, t)`: the point at arc length `s` and `t` metres left of the centre-line. `sidewalk_at(road, side, s)`: the sidewalk centre line (`±(width/2 + sidewalk/2)`; 1.5 m if the side has none).
* `lane_center(road, s, direction)`: one-way roads: if one lane, the centre-line, else `−(width/lanes)/2`; two-way: `per = max(1, lanes//2)`, `lane_w = width/(2·per)`, forward at `−lane_w/2`, backward at `+lane_w/2` with reversed heading.
  `drive_route(road, s0, s1, dir, step=10)` = lane-centre points every 10 m.
* `kerb_slots(road, side, spacing=7, margin=6, offset=1.2)`: parked-car positions every 7 m between `trim + 6 m` and `end − trim − 6 m`, at `±(width/2 − 1.2)` from the centre-line.
* `walk_time(a, b)`: `max(30, 5·ceil((route length / 1.2 · 1.6 + 8) / 5))` seconds (1.2 m/s, 60 % margin, +8 s, rounded up to 5 s); straight-line ×1.4 if no route.

## Part II · L. The scenario file (`dsl/builder.py`)
* **Entities:** the participant `User` (pedestrian body 0.6 × 0.6 × 1.75 m, mass 75 kg) is an inline `Pedestrian`; NPC walkers likewise (default speed 1.3 m/s); vehicles are inline `Vehicle`s with
  bounding box **width 2.0, length 4.6, height 1.5 m, centre offset (1.4, 0, 0.75)** and axles (front 0.5/0.8/1.68/2.98/0.4, rear 0/0.8/1.68/0/0.4), max speed 50, acceleration 8, deceleration 10;
  category car (bus/truck by model prefix); the reference point is the **rear axle**. Models: car_white, car_red, car_blue, car_yellow, van_red, bus_blue, truck_yellow (visual only; all share the same box).
* **Init:** a `TeleportAction` to each entity's start (heading included) and speed 0; initial signal states.
* **Movers:** a `FollowTrajectoryAction` over a polyline with vertex times = cumulative distance / speed (speed ≥ 0.1 m/s), started by `when_time(t)`, `when_user_within(m)` (RelativeDistance < m, centre-to-centre)
  or `when_task_starts/done(task)` (StoryboardElementStateCondition on the task's event).
* **Signals:** a story with one event per phase change: the first change at `offset + (red if initial red else green)` seconds, then alternating `green`/`red` durations until the horizon.
* **Tasks:** one event per task (`task_<id>_<name>`) in a single maneuver; its start trigger is `SimulationTime ≥ start_time` plus one `StoryboardElementState endTransition` condition per dependency.
* **Horizon:** each task ends at `start + baseline timeout` (start = max of `start_time` and the ends of its dependencies); `horizon = max end + 5 s` (30 s + 5 if no tasks); a `StopTrigger` fires at the horizon.
* **Category per task** is derived from the formulas (`spec.axes.category_of`): path > dynamic > static > road > environment.

## Part II · M. Validator constants (`validate.py`)
Walking speed `1.2 m/s`; initial timeout must be `≥ need·1.15 + 3` (suggested `≥ need·1.5 + 5`); baseline above `max(240, need·8)` is warned; HUD text ≤ 160 characters; tolerance outside 0.5–5 m is warned;
scenario horizon over 900 s is warned; pedestrians must start on sidewalk/crosswalk/path/ground; vehicles on the road (surface road/crosswalk, or within `width/2 + 0.3 m` of a centre-line);
moving vehicles faster than `limit·1.6 + 1` m/s are warned; walker speed outside 0.4–2.5 m/s is warned; parked cars within 2.5 m of the participant are an error, within 4 m of each other a warning;
vehicle routes must stay on roads; a crossing task starting >25 m from its crossing is warned. Specification rules: see section 4. Archetype rules read the formulas.

## Part II · N. Sandbox constants (`sandbox.py`)
Script ≤ 30,000 characters and ≤ 20,000 AST nodes; allowed imports `usg.dsl`, `usg`, `math`, `typing`, `scenariogeneration(.xosc)`; denied names (`eval exec open getattr type object os sys …`) and attributes (`format`, anything
starting with `_`, file/serialisation methods); a tiny builtins table; subprocess on the *base* interpreter with a scrubbed environment (only `SYSTEMROOT, TEMP, TMP, PATH`), wall-clock timeout 30 s,
memory cap 1,536 MB, Windows Job Object with a one-process limit and kill-on-close, recursion limit 400. The host serialises results; the script never writes files.

## Part II · O. The local model and the agent (`llm.py`, `localllm.py`, `agent/loop.py`)
* **Model files:** every `*.gguf` under `~/.lmstudio/models` except `mmproj*` and non-first shards; preferred: a name containing `qwen3.5-4b`, then `qwen3.5`, `qwen2.5-coder`, `qwen`, else the first.
* **Engine:** LM Studio's bundled `llama-server` (newest `llama.cpp-*` extension; kinds vulkan / cuda / cpu; `auto` = vulkan, cuda, cpu). Started with `-m model -c ctx -ngl 99 --host 127.0.0.1 --port 8089 --jinja`
  (`-ngl 0` on CPU; `--mmproj file` when the map image is used). Context 16,384 in the app. A Job Object (`KILL_ON_JOB_CLOSE`) kills it when the app dies.
* **Requests:** OpenAI-style streaming chat, temperature 0.2, top_p 0.9, `max_tokens` 1,800, `enable_thinking: false`, timeout 600 s; the stream stops once a `</tool>` closes (one tool call per turn).
  Reasoning blocks are stripped from replies before parsing.
* **Agent limits:** 16 steps (22 at L1/L2); ≥5 lookups trigger a "submit now" nudge; ≤4 unreadable replies; ≤6 rejected specifications; ≤6 rejected scripts; history compaction at 80 % of the context
  (an attached image counts ≈800 tokens); tool results truncated at 2,600 characters.

## Part II · P. The player: how the 3D world is generated (`player/src/scene/world.ts`, `props.ts`, `entities.ts`, `SceneView.tsx`)
**Principle: nothing is modelled by hand per map; every mesh is generated from the numbers of `scene_map.json`, the same numbers the validator used.** Axes: map `(x east, y north)` → three.js `(x, up, −y)`.

| element | construction | size / height |
|---|---|---|
| ground | one large disc, centre = map centre | radius = (half the bounds diagonal + 40 m)·1.6, y = −0.02 |
| green / water areas | flat polygon from the area outline | y = 0.01 / 0.00 |
| road asphalt | flat polygon = `bandPolygon(trimmed centre-line, +w/2, −w/2)` (the left and right offset polylines joined into a ring; mitre limit 2) | y = 0.04 |
| sidewalks | **extruded prism** of the offset band between `w/2` and `w/2 + sidewalk width` | height 0.14 m |
| junctions | asphalt polygon (flat, y = 0.04); corner patches as prisms | 0.14 m |
| centre-line dashes (two-way roads) | one `InstancedMesh` of boxes, a dash every 8 m along the trimmed road | 3.0 × 0.14 m, y = 0.055 |
| crosswalk bars | `InstancedMesh`: `n = floor(length / 1.0 m)` bars across the road, evenly spaced | each 0.5 m wide, depth = crossing width × 0.92, y = 0.06 |
| paths | flat band | width from the map (2.0 or 6.0 m default), y = 0.05 |
| railways | flat band | 2.4 m wide, y = 0.05 |
| barriers | prism of a 0.16 m wide band | height from the map (1.2 m default) |
| **buildings** | `ExtrudeGeometry` of the footprint polygon, counter-clockwise | **height = the map's height (tag or levels × 3 m, ≥3 m)**; colour from a 7-colour palette indexed by a hash of the building id |
| props | one procedural low-poly group per type, placed at the prop position, rotated by its heading | see below |
| signal heads | pole + box + red/green spheres, 0.6 m beyond the crossing's far end, recoloured every frame | pole 2.6 m |
| lighting | sky shader, hemisphere light (0.9), directional light (1.6), fog 120–520 m | – |
Prop primitives (metres): bus stop = roof 1.4×0.1×3.2 at 2.4 m, two posts, translucent back panel 1.5×3.1, bench 0.35×1.8, sign pole 2.9; waste basket = cylinder r 0.22, h 0.75 with a lid;
bench = seat 0.45×1.6, back 0.4 m high, two legs; tree = trunk r 0.18 × 2.2 m + icosahedron crown r 1.7 at 3.6 m; street lamp = pole r 0.07 × 6 m + 0.9 m arm + bulb; bollard = cylinder r 0.1 × 0.9;
bicycle parking = four hoops 0.8 m high. Any prop type can be replaced by a glTF listed in `assets/manifest.json` (`{"bus_stop": "assets/bus_stop.glb"}`); unknown types become a purple 0.4 m cube.
Entities (`entities.ts`): vehicles = box body from the file's bounding box (height factor 0.5 car, 0.6 truck, 0.95 bus; cab box; four wheels r 0.34 m); walkers = capsule r 0.22 / 0.9 m + head sphere r 0.15 at 1.62 m;
the participant is only a 0.28–0.34 m ring on the ground (you are the camera). Task markers: a torus with the radius of the **goal zone the task is judged against** (the formula's zone; legacy tasks: their tolerance),
a translucent beam (5 m) and a bobbing cone at 2.2 m; for every `near_path` corridor a translucent ribbon of half-width `tol` and a thin yellow centre ribbon.
**Camera and movement:** field of view 70°, eye height 1.65 m, near/far 0.05/2000. Desktop: pointer-lock look, WASD or arrows at 1.6 m/s, Shift 2.6 m/s, eye height fixed. VR: `XROrigin` at the start, left stick locomotion 1.6 m/s,
right-stick snap turn 30°, physical walking moves the head; a 4 s countdown before the clock starts; a head-locked text panel 1.5 m ahead (1.5 × 0.42 m) shows the active task and the last message.
**The ego position given to the simulation is the camera/head position projected to the ground; the gaze is the camera's forward direction projected to the ground** (`atan2(−dz, dx)`).

## Part II · Q. The player runtime (`runtime/sim.ts`)
Time step clamped to 0.1 s per frame. Entities follow their trajectory by linear interpolation between vertices (heading from the segment, speed = segment length / duration; after the last vertex they stop).
Conditions: simulation time; StoryboardElementState (start/end/standby/running/complete of acts and events); RelativeDistance (centre-to-centre, or *free-space* = distance to the entity's oriented box).
Tasks: activated by their events; a sequential task whose predecessor failed or was skipped is **skipped**; a hint "Hurry up" at the initial timeout; fail at the baseline timeout; at the StopTrigger all active tasks fail with `timeout`.
The scenario ends 2.5 s after all required tasks are resolved. Formula monitoring: 10 Hz trace per task (`SAMPLE_DT = 0.1`), provisional evaluation at most every 0.04 s, speed from consecutive samples, collision radius of the
participant 0.3 m (`collision_free(r = 0.3)`), see sections 3.4 and 5.

`xodr.py` · `dsl/core.py` (map helpers) · `dsl/builder.py` (boxes, triggers, horizon, auto user 18 m) · `validate.py` · `sandbox.py` · `spec/*.py` (limits, library, nominal walker 1.3 m/s, yield margin 0.8 m) ·

## Part II · S. Known simplifications (state them as limitations)
Flat terrain (no elevation); buildings are plain extrusions (no roofs, windows or textures); sidewalks are assumed where OSM is silent; one-way/two-way lane layout is a simple rule; every vehicle has the same box;
crosswalk bars use a fixed 1 m pitch; junction asphalt is a polygon of the incident road edges (no curbs radii); props are placeholders; trees, lamps and bollards are single nodes (no rows); no traffic-light logic beyond fixed
red/green cycles; the OpenDRIVE junction connections are straight through the junction centre.
